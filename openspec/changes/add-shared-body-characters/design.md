# Design

## Context

See `proposal.md` for motivation. The current canonical adult profile contains 180 anatomical/articulation records; `SkeletonBackend.make_rig` reconstructs `AnatomicalControls` from their rest transforms. Anatomical mesh primitives follow those controls through rigid carriers. `prepare_skeleton` already solves beat-keyed action intent into backend-independent frames and FK deltas, while `api.render` consumes the sealed result. There is no existing body surface or skin-weight source to preserve.

The existing `male_weights` and `female_weights` are alternative coefficients for the same approximate mass-point model. They are unrelated to selecting a visible character. Mobility reference observations likewise do not select character behavior.

## Goals / Non-Goals

**Goals:**

- Make `skeleton`, `male` and `female` equally selectable character IDs while sharing exactly one prepared movement, anatomical profile and rig.
- Make the common surface topology, attachment rules and deformation reusable; store silhouette differences as data.
- Make a movement edit, common surface edit and intentional skeletal compatibility migration observable across the whole registered set in one regeneration/check operation.
- Freeze a small original mannequin dossier that is implementable without an external asset, remesher, auto-weighting operator or new dependency.

**Non-Goals:**

- Measured sex-specific anatomy, muscle geometry/simulation, clinical claims, photorealistic faces, hair, separate cloth simulation, unrestricted body sculpting, external character import, export/bake or retargeting.
- Different skeletal shoulder/hip spacing, limb ratios, stature between characters within one request, or athletic/other body-type presets in this iteration. Existing request-wide uniform stature scaling remains supported.
- General pose/segment/motion composition beyond the already supported diagnostic and consumer-motion language.

## Decisions

### 1. Keep four independent identities

The dependency graph is:

```text
skeletal profile + mobility + movement intent --> prepared poses/timelines
             |                                      |
             +-----------------+--------------------+
                               v
                         shared anatomical rig
                               |
                 +-------------+-------------+
                 v                           v
       skeleton geometry             body-surface template
                                             |
                                 +-----------+-----------+
                                 v                       v
                          male appearance         female appearance
```

Character ID is not a boolean sex flag. A descriptor references a compatible skeletal profile, a renderer kind (`skeletal` or `skinned-surface`), and, for a surface only, one template and one appearance preset. `skeleton` has no template/preset reference, does not instantiate hidden body surfaces and remains a normal consumable character. Common shape rules live in the template, never in copied male/female code. Both surface variants have the same vertex/face IDs and weight assignments; only rest vertex coordinates and declared material values may differ.

Use canonical authored YAML under `characters/`: `registry.yaml` (ordered IDs `skeleton`, `male`, `female`), `definitions/<id>.yaml`, `templates/exercise-mannequin-v1.yaml`, and `appearances/<id>-v1.yaml`. Versioned JSON Schemas close all fields and local references. Each source has description, CC-BY-4.0 license and authored/adapted provenance as applicable. A descriptor's dependency closure is exact; cycles, unknown fields/constructors, unresolved carriers, incompatible profiles, duplicate IDs and executable expressions fail before output allocation or Blender launch. Template/preset documents cannot add action tracks, root adjustments, motion overrides or camera settings.

The template declares `compatible_profile: adult-reference-v1`, `template_revision: 1`, `binding_revision: 1`, the required stable structure/attachment IDs and an expected rest-contract digest. Derive that digest from canonical unscaled rest transforms, carrier hierarchy and contact attachments actually used by the template, not arbitrary YAML formatting or the caller's stature. A bind-significant skeleton edit invalidates the binding until the template's compatibility record is deliberately regenerated and all-character checks pass. Cosmetic skeletal primitive edits that do not affect this rest contract need no new bind. Never silently accept changed joint centers using an old bind.

**Alternative:** three complete profile/motion trees would make synchronization manual. A generic imported humanoid rig would lose existing shoulder, forearm and knee coupling and require asset clearance. Neither is needed for the chosen shared proportions.

### 2. Select appearance at render time

Add `characters: Sequence[str] = ("skeleton",)` to the existing public `render`; add `--characters ID [ID ...]` to `run-blender`. `prepare` and its result remain character-independent. Selecting one character uses a one-item sequence; `("skeleton", "male", "female")` is the complete batch. Reject a bare string, empty sequence, duplicates and unknown IDs. Normalize valid selection to registry order, so request order is not an identity or ordering difference. Batch execution solves no new motion and builds one shared rig. Per-sample visibility selects exactly one character for each image; other character collections and controls are excluded from rendering.

This choice directly fits the current split: profile/stature/actions are preparation concerns, appearance is a render concern. It also avoids tripling pose IDs and avoids a hidden dependency of skeleton preparation on surface data. Import, preparation and skeleton-only selection must not parse or instantiate a surface template. Package-wide byte integrity checks remain in force and are distinct from this semantic dependency rule.

Add immutable result records `CharacterInfo` (ID, renderer kind, profile, template/preset IDs and revisions where present, closure hashes) and `CharacterArtifactSet` (character ID and artifact paths). `GenerationResult` gains ordered `characters`, `character_artifacts`, `character_provenance` and `render_identity` fields. `RenderedImage` gains an additive `character_id` field defaulting to `skeleton` for source compatibility with its existing three-argument construction. Existing pose/sample/timeline fields keep their meaning. A batch image is uniquely keyed by `(character_id, sample_id, view)`; a timeline is reused by every character. Portable projections retain detached data and exact times.

The common `artifacts` map retains its current keys/paths, including the legacy filename `skeleton.blend`; that saved scene contains the common rig and selected character collections. Root `evaluated.json` and `geometry-reference.json` retain their skeletal meanings. Surface evidence is additional under `characters/<id>/surface-reference.json` and `surface-evaluated.json` (or indexed per-sample chunks referenced by that manifest). It must never be passed off as the existing rigid skeletal geometry contract. In no-images mode image collections remain empty; render-only mode provides no invented surface numeric evidence.

For skeleton images preserve `<fixture>/<view>/<frame>.png` under the frame root, both alone and in a batch. Surface images use `<character>/<fixture>/<view>/<frame>.png`. Thus skeleton callers keep their paths and a batch has no collisions. Skeleton expected views remain unchanged, including existing neutral/rest thorax inspection views. Each surface character has front/side for every sample and rear for neutral/rest; isolated skeletal thorax views are not part of its image inventory. The ordinary `render-manifest.json` retains its current shape for skeleton-only selection and has an additive render-identity reference. Any selection containing a surface uses explicit format `character-render-manifest/v1`, with ordered character entries and their complete sample/view/path inventories; there is no implicit character inferred from a filename.

### 3. Seal the render selection without changing motion identity

Host render preflight first validates the persisted preparation through the existing pipeline. It then validates the selected descriptor closure, schema, rest compatibility and resolved template/preset values using installed resources. Persist an additional canonical `character-render-request/v1` record in the owning output run only after request/path/source preflight succeeds. It contains the prepared content hash, normalized character descriptors, selected logical source hashes, resolved numerical surface/weight identity and the active package/backend identity. Its content seal is the `render_identity`; it excludes absolute installation/output paths and timestamps. The supervisor passes the expected render identity, independently of the existing expected prepared identity, to Blender.

Additional native midpoint samples are also host-precomputed request data. Before sealing a full-construction request selecting a surface, the validated host computes the ordered undelivered key-midpoint schedule for selected resolved fixtures and solves those samples from the preparation's already validated scaled profile/mobility/diagnostic sources. Consumer fixtures use their sealed resolved definition and inherited bases, never the original caller file. Store the resulting `native_midpoint_samples` list inside `character-render-request/v1`; each record has deterministic unique `id`, `fixture`, `beat`, `frames`, `guides`, `world_root` and `contacts` fields in the shape already consumed for native-only measurement. Use fixture-ID/beat order and exact rational planning to deduplicate against delivered beats: construct fractions directly from validated integer keys and persisted numerator/denominator pairs, compute `(left+right)/2` exactly and use exact set membership before converting a supported half-integer to its finite numeric evidence value. Include all solved records in `render_identity`, not an unsealed sidecar or mutable backend callback. Skeleton-only and render-only requests use an explicit empty audit list and claim no midpoint evidence. This does not add samples to the public preparation, delivered pose inventory, timelines or images.

Blender uses only standard-library/HML code, verifies both expected identities and package byte hashes, reconstructs the selected numerical surface deterministically, and checks its reconstruction digest. It does not import host YAML/schema packages or accept an unvalidated arbitrary character mapping. Receipts, script phases, metadata, character manifests and result fields identify this same render request. Changing a preset after host preflight, resealing a different selection, swapping one batch entry, or reusing a previous character's image must fail closed. A complete successful receipt hashes the union of all common and selected-character artifacts/images; a missing member prevents success for the entire batch.

Authored character sources and inherited skeleton/mobility/motion provenance remain distinct. `character_provenance` is separate from the unchanged `prepared.provenance`; both are required to attribute a surface result. A skeleton result exposes its character descriptor provenance but no invented surface source. Documentation presents the union, including all nested register references.

### 4. Authored surface dossier, frozen for Gate 1

All dimensions below are original design choices in units of stature `H`, not anatomical measurements or prescriptions. Canonical YAML stores explicit numeric values and declarative named constructors; it contains no executable formulas. The common generator implements the formulas below. Human Gate 1 approves this deliberately simple visual scope; Gate 2 judges its rendered readability. Deviations from the frozen dossier return to the architect/spec workflow instead of being silently tuned in Blender.

#### 4.1 Representation and coordinates

Use six closed, smooth-shaded output mesh components in deterministic order: `torso` (including the connected shoulders and both arms/mitten hands), `head`, `leg.R`, `leg.L`, `foot.R`, `foot.L`. The five declarative geometry-source entries remain torso/head/right-arm/right-leg/right-foot; source region IDs and surviving vertex IDs remain available inside the assembled torso. Sections R4 and R5 below define the local shoulder topology replacement and its refinement; R4 counts describe the coarse construction input to R5. Leg/torso, neck/head and ankle/foot overlaps remain intentional mannequin junctions. A welded whole-body or simulation-ready surface is not claimed. There are no overlapping shoulder caps; open cracks or detached limbs in acceptance views fail human review.

Use 32 equally spaced vertices per loft ring. Subdivide each interval between listed control rings into four equal intervals; interpolate centers/radii linearly and interpolate weights with the smoothstep rule below. Triangulate every quad with the same lower-ID diagonal; the intermediate source lofts cap each end with one center vertex/fan before the explicit R4 removal/assembly. Store vertex IDs as component/ring/sector, with cap IDs separate. Head uses 32 longitudes, 16 latitude intervals and single pole vertices. No remesh, random generation, automatic weights, modifiers that change topology, or subdivision-surface dependency is used. The deterministic R5 shoulder-only refinement is part of canonical rest expansion, before skinning; the global loft/head sampling stays fixed. Smooth shading does not alter vertices.

Construct the reference surface in skeletal rest T-pose. Resolve an anatomical landmark in rest by converting its declared neutral coordinate to its attachment carrier's neutral-local space and applying that carrier's rest matrix. This avoids treating anatomical neutral as armature bind rest. All numeric positions scale with the selected request stature; weights, topology and angles do not. Mirror the right limb in code through X=0 with side-ID swaps and corrected winding; never use negative object/bone scale.

For limb lofts, the centerline follows the listed rest joint centers. The section's first axis is the normalized projection of rest-world +Y perpendicular to its centerline; the second is the cross product producing a right-handed frame. Transport the sign continuously along the component; reject a degenerate axis rather than guessing. Left geometry is the reflected right geometry. Limb radii below are `(anterior radius, transverse radius)`; no longitudinal bone length is changed.

#### 4.6 Material and measured silhouette

Both characters use identical opaque flat materials: suit RGB `(0.18,0.32,0.48)`, head/mitten RGB `(0.72,0.68,0.62)`, foot RGB `(0.12,0.16,0.22)`, alpha 1. There are no texture/image assets. The arms' W-to-D section uses the head/mitten material; other limbs use suit. These colors are authored choices under the existing MATERIAL/FLAT Workbench scene. Character distinction must remain in the silhouette, not labels or color.

Measure every retained control-ring center/radius and head/foot extremum from the generated rest vertices against this table within `1e-5H` (native float32 versus source coordinates); analytic source expansion uses `1e-9H`. For R4 shoulder-replaced rows, verify removed root rings by the closed source-construction contract and verify torso control radii from surviving declared sectors using their known ellipse angles; do not invent absent output rings or compare old positional array offsets. Across male/female, face/index topology and normalized weights must match exactly. Female waist width is 0.140H versus male 0.164H; hip width at z=0.470H is 0.216H versus 0.200H. Independently measured neutral/rest slices must preserve these differences within `1e-4H`. They describe these two presets only.

### 5. Shared skinning and independent evidence

Use explicit vertex groups on the unchanged anatomical armature and a single Armature modifier with preserve-volume enabled, no envelope/automatic weighting and no vertex-group masking. All weights are finite, nonnegative, sum to one within 1e-12 in canonical expansion and 1e-6 in Blender. A vertex has at most two influences outside R4 shoulder bridge interiors and at most three inside them; R4 defines their exact weight rule. No influence is pruned to preserve the old two-influence limit. The deterministic interpolation is `s(t)=3t^2-2t^3` on the declared band, with weights `(1-s,s)`; unit-influence regions are exact. Bind matrices are the corresponding canonical rest matrices. No scale animation or extra anatomical control is introduced.

The host/reviewer reference computes normalized dual-quaternion blending of rigid transforms `posed_i * inverse(rest_i)`. Use the largest-weight influence as quaternion hemisphere reference, breaking ties by carrier ID; flip both real/dual quaternion parts when their real dot is negative. Normalize the blended real quaternion and remove the dual component parallel to it. A real norm below 1e-8 fails explicitly. Apply the blended rigid transform to the rest vertex. This kernel is backend-independent, has no third-party runtime dependency and is compared against Blender's evaluated modifier output, never used as a substitute for native output checks.

Full native delivered surfaces must match the reference kernel within `1e-5H`, with per-character/sample worst vertex IDs and residuals. Also evaluate native meshes at the midpoint of each diagnostic key interval not already delivered, including the largest knee, shoulder and forefoot poses. Preserve-volume implementation details may require an architect-reviewed design revision if this comparison fails; the developer cannot silently change the oracle or tolerances. The skeleton still satisfies its unchanged rigid invariants; surface deformation is separately labeled non-rigid.

Blender consumes the sealed `native_midpoint_samples` after checking the expected render/prepared identities, package/source bindings and finite record structure, unique ordered fixture/beat IDs, complete carrier frames and valid supplied root/guide/contact references. It only applies the supplied solved transforms and measures the actual evaluated surfaces; it must not import the diagnostic evaluator or transitively import host source-validation/YAML/schema modules to reconstruct intent. Audit rows remain separate native evidence and the final saved scene is restored to the final delivered pose. The host/reviewer independently reconstructs the required keyed schedule and solutions from validated sources and rejects missing, extra, duplicated or inconsistent native midpoint evidence. Exercise a deliberately nonempty midpoint case, such as BPM60 with fifth-beat delivered intervals and half-beat action-key midpoints; an empty list at BPM90 where midpoints are already delivered cannot establish this backend dependency boundary. Post-preflight changes to any audit record, including deletion or resealing, fail the existing expected-render-identity check. No host site-packages, PYTHONPATH/PYTHONHOME injection, new dependency, weakened native tolerance or public timing change is part of this mechanism.

Dense host surface checks cover every packaged diagnostic at H=1.50/1.70/1.90, every delivered time, keys/contact events and a grid with spacing <=0.01 beats, reusing evaluated rest vertices/weights and canonical solved frames after native agreement is established. Stream extrema/failures rather than retaining repeated full arrays for dense steps. Require finite vertices, no degenerate triangles (area >1e-12H^2), and no whole-component loss or unexplained topology changes. Triangle intersection counts and mannequin-junction overlaps are reported by region; this first surface contract does not claim collision-free extreme anatomical sweeps. Gross visual interpenetration or a disconnected silhouette in the focused exercise pack fails the human gate.

Floor check uses every deformed vertex and threshold z>=-1e-4H, with no exclusion for covered foot vertices. For every declared supporting heel/ball anchor, measure target/sliding against the unchanged skeletal anchor with existing 1e-3H limits, and separately measure closest sole-triangle distance to that actual posed anchor <=1e-3H. The target alone cannot stand in for the visible surface. An ankle/foot seam must have overlapping component surfaces rather than an open crack in neutral, squat and rocker views. Skeletal COM evidence remains the existing approximate model; surface volume does not replace its weights.

#### Failure context and fault-injection verification

The existing supporting-surface scenario requires a measured floor/contact failure to identify the character, the component and vertex or supporting anchor, the beat, the measured residual and its bound. A sample ID alone does not substitute for an explicit beat. Derive fixture and beat from the authoritative prepared sample (or independently reconstructed midpoint/dense schedule), rather than trusting the damaged evaluated row. Preserve the existing report format and failure codes; enrich the existing diagnostic detail/records consistently across delivered, midpoint and dense checks. Include the comparison and units, for example minimum vertex Z in metres against `-1e-4H`, actual posed anchor-to-sole triangle distance against `1e-3H`, or source-world DQ residual against `1e-5H`. Do not change the measurements, oracle, bounds, failure precedence or success semantics to improve a message.

Sample-local malformed evidence uses the same character/fixture/sample/beat/component or anchor context where that location can be resolved. Missing or reordered vertices report the actual and expected counts or identities and at least the first relevant missing/unexpected identity; a structural mismatch has no geometric residual to invent. An inconsistent reported anchor or sole-distance summary reports its measured-versus-expected value and existing consistency bound. A global stale request, source hash, package identity or artifact membership failure instead identifies the affected artifact/field and observed versus expected identity or membership. It is not associated with an arbitrary pose, and must not fabricate a beat, vertex or geometric residual. Where a malformed row prevents resolving a location, identify the unresolved row and the expected inventory rather than trusting its claimed location. This is the application of the approved failure-context requirement to its actual failure scope, not an exception to a measurable contact failure.

Verify these diagnostics through the complete output verifier using disposable fixture copies with the ordinary preflight and integrity checks enabled: (1) a coherently described below-floor vertex, (2) a detached sole with an unchanged actual posed anchor and a recomputed excessive triangle distance, (3) a forged anchor or reported sole distance, (4) a missing evaluated vertex, and (5) stale source/request evidence. Separate a deliberately invalid seal from a semantic geometry fault: the former may fail at the integrity boundary, while the latter must be internally coherent enough to reach the normal measurement path. The test harness may construct its own evidence/receipt fixture but must not bypass or monkeypatch production validation, replace the reference kernel, change canonical sources, or present mutated evidence as a successful production run. Assert failure plus the applicable contextual values; include an unmodified control that reaches the expected native checks. Existing native-midpoint and dense failure records need the same measured context when their geometric bound fails. A helper-only distance or triangle test is not evidence for this end-to-end diagnostic requirement.
